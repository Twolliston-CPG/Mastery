# Lab 1 — Module Design (3h)

## The contract

A module is an **API**. Its consumers should never need to read its implementation.

**`modules/network/`**

| File | What it is |
|---|---|
| `main.tf` | resources |
| `variables.tf` | INPUTS   -- every one with a description and a type |
| `outputs.tf` | OUTPUTS  -- every one with a description |
| `versions.tf` | required_version + required_providers |
| `README.md` | generated by terraform-docs |


## The rules, and why

| Rule | Why |
|---|---|
| **Never** put a `provider` block in a module | Providers are configured by the root module and inherited. A provider inside a module makes it impossible to use with `for_each` or multiple regions. |
| Every variable has `description` and `type` | `terraform-docs` generates the README from them; untyped variables produce terrible errors |
| Add `validation` where a bad value has a confusing failure | Fail at plan time with a clear message, not at apply time with an AWS API error |
| Output everything a consumer might need | A missing output forces a fork or a `data` source lookup |
| Use `name_prefix` over `name` where the provider supports it | Enables `create_before_destroy`; avoids "name already exists" on replacement |
| Never hardcode a region, account, or AMI | Kills reusability |

## Module versioning
```hcl
module "network" {
  source = "git::https://github.com/you/tf-modules.git//network?ref=v1.2.0"
}
module "network" {
  source  = "your-org/network/aws"
  version = "~> 1.2"
}
```
**Never track a branch.** `?ref=main` means your CI can change behavior with no commit in your repo —
an unreproducible build and a genuinely nasty class of incident.

# Lab 2 — `for_each` vs `count` (3h)

## Part 1 — Reproduce the bug (BF-34)

```hcl
variable "subnets" {
  type    = list(string)
  default = ["10.0.1.0/24", "10.0.2.0/24", "10.0.3.0/24"]
}

resource "aws_subnet" "bad" {
  count      = length(var.subnets)
  vpc_id     = aws_vpc.this.id
  cidr_block = var.subnets[count.index]
  tags       = { Name = "subnet-${count.index}" }
}
```
```bash
terraform apply
terraform state list          # aws_subnet.bad[0], [1], [2]
```
Now **remove the middle element** and plan:
```hcl
default = ["10.0.1.0/24", "10.0.3.0/24"]
```
```bash
terraform plan
# Plan: 0 to add, 1 to change, 1 to destroy   <-- it wants to modify [1] and destroy [2]
```
The addresses are positional. `[1]` used to be `10.0.2.0/24` and is now `10.0.3.0/24` — a different
subnet. Terraform replaces it.

## Part 2 — Fix it

```hcl
variable "subnets" {
  type = map(string)
  default = {
    a = "10.0.1.0/24"
    b = "10.0.2.0/24"
    c = "10.0.3.0/24"
  }
}

resource "aws_subnet" "good" {
  for_each   = var.subnets
  vpc_id     = aws_vpc.this.id
  cidr_block = each.value
  tags       = { Name = "subnet-${each.key}" }
}
```
Remove `b` and plan: **1 to destroy, nothing else touched.** Addresses are `["a"]`, `["b"]`, `["c"]` —
stable and meaningful.

## Part 3 — Recover an existing `count` deployment without destroying anything

```bash
terraform state mv 'aws_subnet.bad[0]' 'aws_subnet.good["a"]'
terraform state mv 'aws_subnet.bad[1]' 'aws_subnet.good["b"]'
terraform state mv 'aws_subnet.bad[2]' 'aws_subnet.good["c"]'
terraform plan     # should be EMPTY
```
Or, better, with `moved` blocks so it's reviewable in a PR:
```hcl
moved {
  from = aws_subnet.bad[0]
  to   = aws_subnet.good["a"]
}
```

## Part 4 — Other iteration patterns

```hcl
# toset() for a list of distinct strings
resource "aws_iam_user" "this" {
  for_each = toset(["alice", "bob", "carol"])
  name     = each.key
}

# for_each over a map of objects
variable "services" {
  type = map(object({
    port     = number
    replicas = number
    public   = optional(bool, false)
  }))
}

# Conditional creation -- the one legitimate use of count
resource "aws_nat_gateway" "this" {
  count = var.enable_nat ? 1 : 0
}

# dynamic blocks
resource "aws_security_group" "web" {
  dynamic "ingress" {
    for_each = var.ingress_rules
    content {
      from_port   = ingress.value.port
      to_port     = ingress.value.port
      protocol    = "tcp"
      cidr_blocks = ingress.value.cidrs
    }
  }
}

# flatten a nested loop
locals {
  rules = flatten([
    for sg_name, cfg in var.security_groups : [
      for port in cfg.ports : {
        key  = "${sg_name}-${port}"
        sg   = sg_name
        port = port
      }
    ]
  ])
  rules_map = { for r in local.rules : r.key => r }
}
```

**Tasks:** build each of these and inspect the resulting state addresses. Then explain in writing
when `count` is still correct. (Two cases: the `? 1 : 0` conditional, and N genuinely
indistinguishable resources.)

# Lab 3 — Environments, Remote State, Refactoring (3h)

## Part 1 — Two environments, same modules

**`environments/`**

| Environment | Configuration |
|---|---|
| `dev/` | Single NAT gateway · `t3.micro` · no Multi-AZ · 1-day backups |
| `prod/` | NAT gateway per AZ · `t3.small` · Multi-AZ · 14-day backups |

Same modules, different `.tfvars`. If the two directories contain different *resources* rather than
different *values*, you have two systems that only look alike — and dev has stopped predicting
anything about prod.

Both call the **same modules** with different inputs. That is the whole design. See
`../projects/alpha-cloud-foundation/environments/`.

**Task:** diff your `dev/main.tf` and `prod/main.tf`. The diff should be *only* inputs. If logic
differs, that logic belongs in the module behind a variable.

## Part 2 — Remote state as a data source

```hcl
data "terraform_remote_state" "network" {
  backend = "s3"
  config = {
    bucket = "tfstate-123456789012-us-east-1"
    key    = "alpha/dev/terraform.tfstate"
    region = "us-east-1"
  }
}

resource "aws_instance" "app" {
  subnet_id = data.terraform_remote_state.network.outputs.app_subnet_ids[0]
}
```

**Use it sparingly.** It creates a hard coupling between state files and a deployment ordering
constraint. The looser alternative is publishing values to **SSM Parameter Store** and reading them
with `data "aws_ssm_parameter"` — the consumer then depends on a *contract*, not on another team's
state file layout. That distinction matters and is a good thing to raise in a design discussion.

## Part 3 — Refactor with `moved`

Take a resource currently in your root module and move it into a module:
```hcl
moved {
  from = aws_instance.web
  to   = module.compute.aws_instance.web
}
```
```bash
terraform plan      # MUST show 0 to add, 0 to destroy
```
**Zero destroys is the acceptance criterion.** If the plan wants to destroy and recreate, the move
is wrong.

## Part 4 — Drift (BF-40)
```bash
aws ec2 create-tags --resources <id> --tags Key=ChangedBy,Value=console
terraform plan -refresh-only
terraform apply -refresh-only
aws cloudtrail lookup-events --lookup-attributes AttributeKey=ResourceName,AttributeValue=<id>
```

# Lab 4 — Validation, Linting, Testing (3h)

## The gate stack
```bash
terraform fmt -check -recursive
terraform validate
tflint --recursive --format compact
checkov -d . --framework terraform
```

`.tflint.hcl` and the checkov exception ADR are in the Alpha reference.

## `terraform test`

```hcl
# tests/network.tftest.hcl
variables {
  project     = "test"
  environment = "dev"
  region      = "us-east-1"
  vpc_cidr    = "10.99.0.0/16"
  az_count    = 2
}

run "vpc_cidr_is_applied" {
  command = plan

  assert {
    condition     = aws_vpc.this.cidr_block == "10.99.0.0/16"
    error_message = "VPC CIDR does not match the input"
  }
}

run "app_subnets_are_slash_20" {
  command = plan

  assert {
    condition = alltrue([
      for s in values(local.app_subnets) : tonumber(split("/", s)[1]) == 20
    ])
    error_message = "App subnets must be /20 to leave room for pod IPs"
  }
}

run "data_tier_has_no_default_route" {
  command = plan

  assert {
    condition     = length([for r in values(aws_route.app_nat) : r if r.route_table_id == aws_route_table.data.id]) == 0
    error_message = "The data tier must not have a default route"
  }
}

run "rejects_small_vpc_cidr" {
  command = plan
  variables {
    vpc_cidr = "10.99.0.0/24"
  }
  expect_failures = [var.vpc_cidr]
}
```
```bash
terraform test
```

**`command = plan` tests are fast and free** — no resources created. Use `command = apply` sparingly
for integration tests that need real resources.

The last test is the interesting one: `expect_failures` asserts that a **validation rejects** bad
input. Testing that your guardrails actually guard is more valuable than testing the happy path.
